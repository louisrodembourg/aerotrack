# aerotrack

Real-time vehicle and pedestrian **detection + tracking on drone video**, optimised for
embedded hardware. The deliverable is not a model but an analysis: **how much accuracy
does each optimisation cost or buy, under a fixed latency budget on a given device?**

## Reference constraint

Every variant is judged against one budget (`configs/project.yaml`):

> End-to-end pipeline (preprocess → detection → NMS → tracking) **≥ 25 FPS, batch 1**,
> on the target device.

The target device will be decided at week 6: a Jetson Orin Nano (JetPack 6.x), or a cloud
NVIDIA GPU with TensorRT compared against a CPU running ONNX Runtime. Every latency figure
in this repository states its device, its runtime versions and, on Jetson, its power mode.

## Status

Week 1–2: foundations and zero-shot baseline. The dataset converters, the evaluation
harness (accuracy + latency through a single pipeline), the local smoke test and the
remote training setup are in place. Fine-tuning starts at week 3.

| Weeks | Stage |
|---|---|
| 1–2 | foundations + baseline ← *here* |
| 3–5 | fine-tuning on VisDrone-DET: resolution, P2 head, SAHI, hybrid keyframe mode, copy-paste augmentation → reference detector frozen |
| 6–7 | ByteTrack / BoT-SORT on VisDrone-MOT (TrackEval: HOTA, MOTA, IDF1, IDSW), Kalman filter from scratch, hardware decision |
| 8–10 | ONNX → TensorRT FP16 → INT8 PTQ → INT8 QAT, C++ runtime |
| 11 | robustness: VisDrone → UAVDT transfer by attribute, synthetic degradations |
| 12 | write-up, demo |

## Reproduce

Requirements: [uv](https://docs.astral.sh/uv/). Development happens on macOS Apple
Silicon (MPS) and Linux CUDA, from the same lockfile.

```bash
make setup        # locked environment
make data-min     # VisDrone-DET (~2 GB): enough for the two commands below
make smoke        # ~1 min: short training + evaluation on 100 images, local device
make baseline     # zero-shot COCO YOLO on VisDrone-DET val, accuracy + latency
make data         # everything: + VisDrone-MOT, UAVDT, visualisations, TrackEval checks
make test
```

Training on a remote CUDA machine (Docker + NVIDIA container toolkit, or `--no-docker`
on Kaggle):

```bash
export WANDB_API_KEY=...        # optional: without it, W&B runs stay offline
scripts/remote_train.sh configs/train/visdrone_yolo26s.yaml
```

The script builds `docker/Dockerfile.cuda` and downloads and converts the data itself,
then trains and evaluates. The run lands in W&B and in `runs/<id>/run.json` (config,
commit, seed, device, environment, metrics, weights).

## Data

| Dataset | Use | Format produced |
|---|---|---|
| VisDrone2019-DET | detection training / evaluation | YOLO labels + ground-truth JSON, ignored regions kept apart |
| VisDrone2019-MOT | tracking evaluation | TrackEval MOTChallenge, one benchmark per evaluated class |
| UAVDT-Benchmark-M | transfer and robustness (vehicles) | both of the above, plus per-sequence attributes |

Ignored regions are masked during training and removed at evaluation with each dataset's
official rule. Class mappings, including the classes excluded from the COCO baseline,
are explicit in `configs/data/class_maps.yaml`.
