# aerotrack

Real-time vehicle and pedestrian **detection + tracking on drone video**, optimised for
embedded hardware. The deliverable is not a model but an analysis: **how much accuracy
does each optimisation cost or buy, under a fixed latency budget on a given device?**

## Reference constraint

Every variant is judged against one budget (`configs/project.yaml`):

> End-to-end pipeline (preprocess → detection → NMS → tracking) **≥ 25 FPS, batch 1**,
> on the target device.

The target device will be decided at week 6: a Jetson Orin Nano (JetPack 6.x), or a cloud
NVIDIA GPU with TensorRT compared against a CPU running ONNX Runtime. Every latency figure
in this repository states its device, its runtime versions and, on Jetson, its power mode.

## Status

Week 4: resolution sweep. YOLO26n was chosen as the primary axis (it alone keeps margin
under the budget on CPU) and fine-tuned at 640, 960 and 1280 on VisDrone-DET (100 epochs,
on Kaggle's free T4s), evaluated on test-dev with latency on the Mac; a P2 (stride-4) head
was then compared at 640 and 960. Week 5: tiled (SAHI-style) inference, measured against
training at the higher resolution. Next: hybrid keyframe mode and copy-paste augmentation.

| Weeks | Stage |
|---|---|
| 1–2 | foundations + baseline |
| 3–5 ← *here* | fine-tuning on VisDrone-DET: resolution, P2 head, SAHI, hybrid keyframe mode, copy-paste augmentation → reference detector frozen |
| 6–7 | ByteTrack / BoT-SORT on VisDrone-MOT (TrackEval: HOTA, MOTA, IDF1, IDSW), Kalman filter from scratch, hardware decision |
| 8–10 | ONNX → TensorRT FP16 → INT8 PTQ → INT8 QAT, C++ runtime |
| 11 | robustness: VisDrone → UAVDT transfer by attribute, synthetic degradations |
| 12 | write-up, demo |

## Results

All numbers below are generated by `make readme` from tracked runs (`reports/`); each
row names its run id. Methodology: [DECISIONS.md](DECISIONS.md).

### Findings so far

All on VisDrone-DET test-dev (1610 images never used for training or checkpoint
selection), mAP50-95 in %; latency on an Apple M3 Pro on AC power, detection only
(tracking not yet in the pipeline).

- **Fine-tuning is the first-order gain.** On the six classes COCO can name, YOLO26n goes
  from 4.1 zero-shot to 19.1 fine-tuned, YOLO26s from 7.9 to 23.3
  ([w3-vs-zero-shot](reports/w3-vs-zero-shot/results.md)).
- **YOLO26n is the primary axis.** s adds 3.6 points on the ten VisDrone classes (14.2 →
  17.8) but is the only one of the two to miss 25 FPS on CPU
  ([w3-reference](reports/w3-reference/results.md)).
- **Resolution is the strongest lever for small objects.** YOLO26n at 640 / 960 / 1280:
  14.2 / 19.0 / 22.5 mAP, AP_small doubling from 6.4 to 12.9. On CPU, inference time
  grows with pixel count, so only 640 stays within 25 FPS; on MPS all three do
  ([w4-resolution](reports/w4-resolution/results.md)).
- **A P2 (stride-4) head adds 1.2 points** at both 640 and 960, for 15 to 45 % more
  latency. On GPU, resolution buys more per millisecond (plain 1280 beats P2 at 960); on
  CPU, P2 at 640 is the most accurate model within the budget: 15.4 mAP at 33 FPS
  ([w4-p2](reports/w4-p2/results.md)).
- **Tiled inference (SAHI-style) helps, but training at the target resolution helps
  more.** Cutting each frame into 2x2 tiles plus the whole frame lifts the 640 model from
  14.2 to 18.1 mAP (27.9 ms on MPS); the model trained at 1280 reaches 22.5 in a single
  pass for 23.5 ms ([w5-sahi](reports/w5-sahi/results.md)).

## Reproduce

Requirements: [uv](https://docs.astral.sh/uv/). Development happens on macOS Apple
Silicon (MPS) and Linux CUDA, from the same lockfile.

```bash
make setup        # locked environment
make data-min     # VisDrone-DET (~2 GB): enough for the two commands below
make smoke        # ~1 min: short training + evaluation on 100 images, local device
make baseline     # zero-shot COCO YOLO on VisDrone-DET val, accuracy + latency
make w3-eval      # each week's evaluation on test-dev (after pulling its runs), then README
make w4-eval
make w4-p2-eval
make w5-sahi-eval
make data         # everything: + VisDrone-MOT, UAVDT, visualisations, TrackEval checks
make test
```

Training runs on a remote NVIDIA GPU. Two ways, same tracked run at the end
(`runs/<id>/run.json`: config, commit, seed, device, environment, metrics, weights):

**Kaggle (free 2 × T4), driven from your machine.** Needs a Kaggle account with a
verified phone number and an API token under `~/.kaggle/` (`kaggle.json` or `access_token`).

```bash
uv run aerotrack kaggle push configs/train/visdrone_yolo26n_640.yaml \
    configs/train/visdrone_yolo26s_640.yaml --slug aerotrack-w3-ref   # one job per T4
uv run aerotrack kaggle status aerotrack-w3-ref
uv run aerotrack kaggle pull aerotrack-w3-ref                         # merge runs into runs/
```

A Kaggle GPU session stops at about 12 h; the kernel interrupts jobs at 11 h 15 and keeps
their checkpoints. `--resume <run id>` continues such a run in a new session from its
last epoch (same optimizer state and schedule), as a new run linked to the interrupted one:

```bash
uv run aerotrack kaggle push configs/train/visdrone_yolo26n_p2_960.yaml \
    --slug aerotrack-w4-p2-resume --resume 20261027-222023-visdrone-yolo26n-p2-960-93f3b8
```

The kernel carries the committed code (uncommitted changes are refused), installs the
same locked environment, downloads and converts the data, and trains. For live W&B
logging, add a `WANDB_API_KEY` secret to the kernel once in Kaggle's editor; otherwise
the runs come back offline and `wandb sync` uploads them.

**Any CUDA box with Docker** (or `--no-docker` on the host):

```bash
export WANDB_API_KEY=...        # optional: without it, W&B runs stay offline
scripts/remote_train.sh configs/train/visdrone_yolo26s_640.yaml
```

## Data

| Dataset | Use | Format produced |
|---|---|---|
| VisDrone2019-DET | detection training / evaluation | YOLO labels + ground-truth JSON, ignored regions kept apart |
| VisDrone2019-MOT | tracking evaluation | TrackEval MOTChallenge, one benchmark per evaluated class |
| UAVDT-Benchmark-M | transfer and robustness (vehicles) | both of the above, plus per-sequence attributes |

Ignored regions are masked during training and removed at evaluation with each dataset's
official rule. Class mappings, including the classes excluded from the COCO baseline,
are explicit in `configs/data/class_maps.yaml`.
